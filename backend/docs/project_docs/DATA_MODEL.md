# Модель данных

**Назначение:** описать фундамент системы до создания БД и экранов.

## 1. Основной принцип

Система различает штатную структуру, реальных людей и фактические профили работы:

```text
Подразделение -> Штатная строка -> Назначение сотрудника -> Профиль сотрудника
                                      |
                                      -> принятые версии -> Профиль должности
```

Одна штатная строка может быть вакантной либо занята несколькими сотрудниками с долями ставки. Это нормальная ситуация, а не ошибка.

## 2. Организационная структура

### `OrgUnit`

Подразделение или узел организационной иерархии.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `name` | Название |
| `parent_id` | Вышестоящий узел |
| `path` | Материализованный путь для отображения/поиска |
| `source_snapshot_id` | Источник импорта |
| `is_demo` | Признак демо-данных |
| `is_active` | Актуальность |

### `StaffingLine`

Строка штатного расписания: должность в конкретном подразделении и объём ставок.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `org_unit_id` | Подразделение |
| `title` | Название должности |
| `approved_fte` | Ставок по ШР |
| `reported_occupied_fte` | Занято по импортированному ШР |
| `source_row_key` | Ссылка на строку импорта |
| `is_demo` | Демо-признак |
| `is_active` | Актуальность |

### `Employee`

Пользователь/сотрудник, добавленный HR или импортом.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `external_employee_id` | Кадровый ID, если имеется |
| `full_name` | ФИО |
| `email` | Email для доступа/приглашений |
| `system_role` | Системная роль: сотрудник, HR, администратор |
| `is_demo` | Признак демонстрационной личности |
| `is_active` | Активность |

Сотрудник не создаётся саморегистрацией в MVP. Его добавляет HR или импорт.

### `AuthLoginToken`

Одноразовая ссылка входа для локального magic-link сценария.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `employee_id` | Сотрудник, для которого выпущена ссылка |
| `token_hash` | SHA-256 хэш одноразового токена; сырой токен не хранится |
| `expires_at` | Срок действия ссылки |
| `consumed_at` | Время использования ссылки |
| `created_at` | Время выпуска |

### `AuthSession`

Активная backend-сессия после входа по magic-link.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `employee_id` | Авторизованный сотрудник |
| `token_hash` | SHA-256 хэш bearer-токена; сырой токен не хранится |
| `expires_at` | Срок действия сессии |
| `revoked_at` | Время logout/отзыва |
| `created_at` | Время создания сессии |
| `last_seen_at` | Последнее использование сессии |

### `Assignment`

Назначение сотрудника на штатную строку.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `external_assignment_id` | ID назначения из рабочего импорта; различает несколько назначений одного сотрудника |
| `employee_id` | Сотрудник |
| `staffing_line_id` | Штатная строка |
| `fte` | Доля ставки |
| `manager_assignment_id` | Непосредственный руководитель |
| `assignment_role` | Основное/совмещение/иное |
| `valid_from` / `valid_to` | Период действия |
| `is_demo` | Демо-признак |

Для рабочего импорта CSV/XLSX одна строка описывает одно назначение, а не просто
человека. Обязательные колонки: `ID назначения`, `ID сотрудника`, `ФИО`, `Email`,
`Путь подразделения`, `Должность`, `Ставка`. Опционально передаются
`ID назначения руководителя` и `Роль` (`employee` / `manager`).

Рассчитываемый остаток вакансий:

```text
vacancy_fte = approved_fte - сумма активных Assignment.fte
```

## 3. Кампании

### `Campaign`

| Поле | Назначение |
|---|---|
| `id` | ID кампании |
| `name` | Название |
| `status` | Черновик / активна / закрыта / архив |
| `start_at` / `due_at` | Период |
| `is_demo` | Демо-признак |
| `created_by` | HR-создатель |

### `CampaignParticipant`

Отделяет присутствие человека в структуре от ожидания профиля.

| Поле | Назначение |
|---|---|
| `campaign_id` | Кампания |
| `assignment_id` | Участник в конкретной позиции |
| `participation_status` | Включён / исключён / отложен |
| `expected_to_submit` | Ожидается ли заполнение |
| `included_by` | Кто включил |
| `inclusion_reason` | Причина/массовая операция |

## 4. Профили и версии

### `EmployeeProfile`

Рабочая карточка профиля конкретного назначения сотрудника в конкретной кампании.

| Поле | Назначение |
|---|---|
| `id` | ID профиля |
| `campaign_participant_id` | Участник кампании |
| `current_draft_id` | Текущий редактируемый черновик |
| `latest_submitted_revision_id` | Последняя сданная версия |
| `accepted_revision_id` | Версия, принятая HR |
| `workflow_status` | Текущий статус процесса |
| `progress_percent` | Прогресс обязательных полей |

### `ProfileDraft`

Редактируемая рабочая область. Автосохраняется и может быть сохранена для продолжения позже.

### `ProfileRevision`

Неизменяемый снимок при сдаче, пересдаче или служебной фиксации.

| Поле | Назначение |
|---|---|
| `id` | ID версии |
| `employee_profile_id` | Профиль |
| `revision_no` | Последовательный номер |
| `based_on_revision_id` | Версия, из которой создана новая редакция |
| `answers_json` | Снимок ответов |
| `submitted_at` | Время сдачи |
| `assistant_mode` | `off`, `unavailable`, `external`, `internal` |
| `assistance_level` | `none`, `partial`, `full` |
| `assisted_sections_json` | Разделы с помощью ИИ |
| `ai_check_status` | Не выполнялась / выполнена / ожидает |
| `locked_at` | Время блокировки проверкой/принятием |

### `PositionProfile`

Консолидированный профиль штатной позиции или класса однотипных позиций. Формируется HR на основании принятых профилей сотрудников и подтверждённых документов; не заменяет индивидуальные версии.

## 5. Документы

### `Document`

Карточка документа вне зависимости от его привязки.

| Поле | Назначение |
|---|---|
| `id` | ID документа |
| `document_code` | Регистрационный/децимальный номер или внутренний код |
| `document_type` | `job_instruction`, `unit_regulation`, `professional_standard`, `other` |
| `title` | Название |
| `version` | Версия |
| `valid_from` / `valid_to` | Срок действия |
| `document_status` | Загружен / проверяется / подтверждён / устарел / архив |
| `source_file_path` | Путь к оригиналу |
| `extracted_text_path` | Путь к извлечённому тексту |
| `content_text` | Текст документа или демо-содержание без файла |
| `ocr_quality_status` | Не проверено / есть предупреждения / проверено |
| `checksum` | Контроль дублей |
| `is_demo` | Демо-признак |

### `DocumentLink`

Подтверждённая или предложенная связь документа с объектом структуры.

| Поле | Назначение |
|---|---|
| `document_id` | Документ |
| `target_type` | Подразделение / штатная строка / профиль должности / ветка |
| `target_id` | ID объекта |
| `link_status` | Предложено / подтверждено / отклонено / устарело |
| `confirmed_by` / `confirmed_at` | Подтверждение HR |

Демо-документы могут связываться только с демо-объектами.

## 5.1. Настройки ИИ

### `AiConfiguration`

Единая HR-настройка будущего AI Gateway.

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID конфигурации |
| `mode` | `default`, `off`, `local`, `token` |
| `provider` | `off`, `ollama`, `lm_studio`, `openai_compatible` |
| `base_url` | Адрес локального или совместимого endpoint |
| `model_name` | Имя модели |
| `api_token` | Токен доступа, если выбран режим по токену; не возвращается через API |
| `clarity_threshold` | Минимальный процент понятности ответа, после которого ответ считается достаточным |
| `followup_strictness` | Насколько строго ассистент задаёт уточняющие вопросы: `soft`, `balanced`, `strict` |
| `updated_by_id` | HR, изменивший настройку |
| `updated_at` | Время изменения |

Ollama используется только как локальный интервьюер по одному открытому вопросу анкеты. В модель не передаются ФИО, email, кадровые ID и история действий. Документы и persistent AI-router подключаются отдельно после расширения политики обезличивания.

### `QuestionnaireQuestionSetting`

Глобальная настройка открытых вопросов текущей анкеты до появления версий анкеты.

| Поле | Назначение |
|---|---|
| `question_key` | Ключ вопроса из текущего шаблона профиля |
| `ai_check_enabled` | Нужно ли проверять этот открытый ответ локальным AI-интервьюером |
| `good_example` | HR-пример достаточного ответа, подставляется в анкету и промпт |
| `bad_example` | HR-пример слабого ответа для промпта и подсказки сотруднику |
| `requirements` | Особые требования к достаточному ответу |
| `updated_by_id`, `updated_at` | Кто и когда изменил настройку |

## 6. Проверки и сигналы

Вместо одного понятия аномалии применяются разные классы сигналов:

| Класс | Пример |
|---|---|
| `DataQualityIssue` | Назначение ссылается на отсутствующую позицию; сумма активных ставок выше лимита |
| `DocumentMismatch` | Фактическая обязанность не подтверждается ДИ |
| `UnitCoverageGap` | В положении есть функция, но она не покрыта ДИ/принятыми профилями |
| `RoleOutlier` | Профиль сотрудника заметно отличается от сопоставимых ролей |
| `PotentialResponsibilityOverlap` | Две роли заявляют финальную ответственность за один объект/результат |

Схожие функции сами по себе не являются нарушением: frontend- и backend-разработчики могут оба разрабатывать ПО, отличаясь объектом, результатом и полномочиями.

## 7. Аудит

### `AuditEvent`

Хранит:

- актор и роль;
- действие;
- тип и ID объекта;
- состояние до/после либо ссылку на версию;
- причину массового возврата или административного вмешательства;
- дату и контекст демо/рабочих данных.

Удаление истории версий или событий не допускается штатными пользовательскими сценариями.
