# Процессы, статусы и доступ

## 1. Роли

| Роль | Область видимости | Основные действия |
|---|---|---|
| Сотрудник | Свои назначения и профили | Заполняет, сохраняет черновик, сдаёт, дорабатывает после возврата |
| Руководитель | Свой профиль и доступная административная ветка | Проверяет, комментирует, подтверждает, возвращает профили вниз |
| Руководитель направления / директор | Закреплённая область | Контролирует прогресс и аналитику; права возврата задаются матрицей |
| HR | Все рабочие и демо-данные с явным разделением | Добавляет людей, запускает кампании, ведёт документы, принимает либо возвращает руководителю |
| Администратор | Настройки, роли и технические операции | Настраивает систему |
| Суперадмин | Исключительные операции | Переоткрывает любой процесс с обязательной причиной и аудитом |

В демо один пользователь `Эйчар Эйчарович Эйчаров` может иметь роль HR и быть показан как носитель корневой позиции для иллюстрации структуры.

## 1.1. Вход в систему

В demo-local остаётся быстрый вход демо-пользователем, чтобы проходить сценарии за HR, руководителя и сотрудника. Для рабочего входа используется magic-link контур: пользователь вводит email, backend выпускает одноразовую ссылку, после использования создаётся bearer-сессия. При активной сессии backend определяет актора по `Authorization: Bearer`. Заголовок `X-Demo-User-Id` и список демо-пользователей работают только в `demo-local/test`; в пилотном режиме без bearer-сессии backend возвращает `401`.

В локальном режиме ссылка показывается в интерфейсе для тестирования без почтовой инфраструктуры. В пилоте та же операция должна отправлять ссылку через согласованный почтовый канал. Выпуск ссылки, вход и logout сохраняются в аудите.

## 2. Заполнение сотрудником

1. HR включает назначение сотрудника в кампанию.
2. Для сотрудника создаётся профиль со статусом `Не начат`.
3. При первом ответе появляется редактируемый черновик и статус `В процессе`.
4. Каждый ответ автосохраняется.
5. Кнопка `Сохранить и выйти` позволяет закончить текущую сессию без сдачи.
6. Прогресс считается по обязательным полям/разделам.
7. После заполнения система спрашивает подтверждение сдачи.
8. При подтверждении создаётся неизменяемая `ProfileRevision`.

При выключенном ИИ перед продолжением показывается стандартная самостоятельная проверка ответа, но она не блокирует сдачу.

## 3. Состояния профиля

| Статус | Смысл | Редактирование сотрудником |
|---|---|---|
| `not_started` | Включён, но не начал | Да |
| `draft` | Есть сохранённый черновик | Да |
| `submitted` | Версия отправлена, ещё не взята в проверку | Можно создать новую сдаваемую редакцию |
| `under_review` | Руководитель явно взял версию на проверку | Нет |
| `returned_for_revision` | Возвращён сотруднику на доработку | Да |
| `manager_verified` | Руководитель подтвердил версию | Нет |
| `returned_by_hr` | HR вернул результат руководителю | Сотрудник не редактирует, пока руководитель не направит возврат вниз |
| `hr_accepted` | HR принял версию | Нет |
| `archived` | Процесс закрыт | Нет |

Открытие страницы руководителем не блокирует профиль. Блокировка возникает только после явного действия `Взять на проверку`.

## 4. Версии и повторная сдача

Пример истории:

```text
Черновик
-> сотрудник отправил v1 без ИИ
-> сотрудник уточнил до взятия в проверку и отправил v2
-> руководитель взял v2 на проверку
-> руководитель вернул v2
-> сотрудник отправил v3
-> руководитель подтвердил v3
-> HR вернул руководителю
-> руководитель вернул сотруднику
-> сотрудник отправил v4
-> руководитель подтвердил v4
-> HR принял v4
```

По умолчанию аналитика использует последнюю актуальную версию на текущем этапе, но уполномоченные роли могут просмотреть и сравнить всю историю.

## 5. Возвраты и массовые операции

Руководитель может вернуть:

- один профиль;
- выбранные профили;
- все доступные профили подразделения;
- профили по выбранной нижестоящей ветке.

HR может вернуть результат ответственному руководителю:

- по одному профилю;
- списком;
- по подразделению;
- по ветке.

HR не обязан сразу открывать редактирование сотрудникам: руководитель определяет, кому направить доработку вниз.

Перед массовым возвратом система показывает охват и статусы. Причина обязательна. Система создаёт групповую операцию и индивидуальные задачи по затронутым профилям.

Суперадмин может переоткрыть любой этап только как исключительное действие с причиной; история не удаляется и утверждённые версии не перезаписываются.

## 6. Доступ к документам и аналитике

| Пользователь | Документы | Аналитика |
|---|---|---|
| Сотрудник | Связанные с его профилем документы/фрагменты, разрешённые для показа | Свой статус и прогресс |
| Руководитель | Документы профилей в своей доступной зоне | Своя ветка |
| Директор/направление | Документы в закреплённой зоне | Закреплённая область |
| HR | Весь реестр и привязки | Вся система, с переключателем demo/real |

HR также видит вкладку настроек платформы. В ней можно выбрать режим ИИ:

- `По умолчанию` - использовать серверную конфигурацию;
- `Без ИИ` - гарантированный локальный режим без модели;
- `Локальная ИИ` - заготовка под Ollama или LM Studio;
- `По токену` - заготовка под OpenAI-compatible endpoint с токеном.

Сохранение настроек доступно только через backend-права HR и фиксируется в аудите. Токен не возвращается через API. Сейчас реальный LLM-вызов разрешён только для локального Ollama-интервьюера по одному открытому вопросу.

Если HR включает локальный режим Ollama, сотрудник может проверять открытые вопросы анкеты через локального AI-интервьюера. В модель уходит только обезличенный контекст конкретного поля: вопрос, пример ответа, требования при наличии, текущий ответ и предыдущая итерация уточнения. Если понятность ниже настроенного HR-порога, система показывает уточняющий вопрос и не считает ответ принятым. После повторного ответа в модель передаются предыдущий ответ, предыдущий уточняющий вопрос и текущий ответ, чтобы ассистент пересмотрел процент понятности.

В той же вкладке HR настраивает открытые ответы текущей анкеты: включает или выключает AI-проверку по каждому открытому вопросу, задаёт пример хорошего ответа, пример слабого ответа и особые требования. Эти настройки применяются глобально к текущей анкете; отдельные версии анкеты и закрепление версии за кампанией остаются следующим слоем.

## 7. Прогресс и напоминания

Прогресс нужен и сотруднику, и контролирующим ролям:

```text
Заполнено 8 из 9 разделов. Остался один обязательный ответ.
```

Для будущих напоминаний система должна хранить:

- дату начала заполнения;
- дату последней активности;
- процент прогресса;
- дедлайн кампании;
- дату последнего напоминания.

В demo-local достаточно отображать список почти завершённых и остановившихся черновиков; реальная отправка уведомлений относится к пилотному этапу.
