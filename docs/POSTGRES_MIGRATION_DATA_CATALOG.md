# Каталог таблиц для будущего перехода на PostgreSQL

Дата актуализации: 2026-06-08.

Документ фиксирует текущую логическую модель SQLite MVP и целевую трактовку сущностей для будущего пилотного контура на PostgreSQL. Основной источник требований — `ТЗ_ИИ_профилирование_должностей_бизнес_v2.md`; архивные документы используются только как форматный референс. Демо-данные должны оставаться явно помеченными через `is_demo = true` и не должны участвовать в рабочих KPI по умолчанию.

## Общие правила миграции

- В MVP нет отдельной таблицы `users`: учетная запись и пользовательские роли сейчас хранятся в `employees`. При переходе на PostgreSQL можно оставить эту схему для пилота либо выделить `users` отдельно, но без смешивания кадровой сущности сотрудника, назначения и сессии.
- Текущие JSON-поля в SQLite хранятся как `Text` (`answers_json`, `ai_usage_json`, `assisted_sections_json`, `details_json`). Для PostgreSQL их стоит переводить в `jsonb` с проверками структуры и индексами только по реально используемым ключам.
- Текущие статусы хранятся строками. Для PostgreSQL рекомендуется зафиксировать справочники/`CHECK`-ограничения для ролей, workflow-статусов, статусов кампаний, волн, документов и событий проверки.
- Все таблицы с бизнес-данными должны сохранять демо-признак там, где объект может быть создан в демо-контуре. При миграции нельзя связывать демо-документы с рабочими объектами и наоборот.
- Все изменения статусов, сдачи профилей, возвраты, подтверждения, изменения документных связей и импортные операции должны иметь запись аудита (`audit_events`) или специализированное событие (`profile_review_events`).

Дополняет `profile_review_events`. | Модель: `backend/app/models.py`; авторизация: `backend/app/auth_operations.py`; HR-операции: `backend/app/hr_operations.py`; профили/настройки: `backend/app/profile_operations.py`, `backend/app/settings_operations.py`; документы: `backend/app/document_operations.py`; импорт: `backend/app/work_employee_import.py`, `backend/app/work_staffing_import.py`. | Для PostgreSQL `details_json` лучше `jsonb`, `entity_id` лучше нормализовать по типу или оставить строкой с индексом `(entity_type, entity_id)`. Нельзя терять аудит при миграции, особенно для профилей, документов и назначений. |

## Сущности из требований, которых нет как отдельных таблиц в текущем MVP

| Сущность | Текущее состояние | Рекомендация для PostgreSQL |
|---|---|---|
| `users` | Отдельной таблицы нет; роль, логины и парольный хэш хранятся в `employees`, а сессии — в `auth_sessions`. | Для пилота решить: оставить `employees` как user principal или выделить `users(id, employee_id, role, credentials...)`. При выделении не переносить кадровые поля в auth-контур. |
| `position_profiles` / консолидированные профили должности | Описаны концептуально в `docs/DATA_MODEL.md`, но SQLAlchemy-модели и миграции пока нет. | Создать отдельную таблицу для HR-консолидации по штатной строке/классу позиций: не смешивать с `employee_profiles` и `profile_revisions`. |
| Версии шаблона анкеты | Вопросы профиля сейчас определяются кодом и настройками `questionnaire_question_settings`; версия анкеты не фиксируется за кампанией. | Добавить `questionnaire_versions` и связь кампании/ревизии с версией шаблона, чтобы старые сдачи оставались воспроизводимыми. |
| Версии импортов/оригиналов файлов | Аудит и checksum есть, но отдельной таблицы import batches/file versions нет. | Для PostgreSQL добавить `import_batches`/`document_file_versions`, чтобы хранить источник, версию обработки и качество OCR независимо от карточки документа. |

## Минимальные индексы и ограничения для PostgreSQL

| Область | Индексы / ограничения |
|---|---|
| Auth | Unique `employees.email`/`username` с нормализацией регистра; unique `auth_login_tokens.token_hash`; unique `auth_sessions.token_hash`; индексы по `employee_id`, `expires_at`, `revoked_at`. |
| Оргструктура | Unique `org_units.path`; индексы `org_units.parent_id`, `org_units.department_code`, `staffing_lines.org_unit_id`, `staffing_lines.position_code`, `assignments.employee_id`, `assignments.staffing_line_id`, `assignments.manager_assignment_id`. |
| Кампании | Unique `campaign_participants(campaign_id, assignment_id)`; индексы по `campaign_id`, `campaign_wave_id`, `participation_status`, `expected_to_submit`. |
| Профили | Unique `employee_profiles.campaign_participant_id`; unique `profile_drafts.employee_profile_id`; unique `profile_revisions(employee_profile_id, revision_no)`; индексы по `workflow_status`, `submitted_at`, `profile_review_events(employee_profile_id, created_at)`. |
| Документы | Unique `documents.document_code`; индекс/unique strategy по `checksum`; unique `document_links(document_id, target_type, target_id)`; индексы по `target_type, target_id`, `link_status`, `is_demo`. |
| JSON/audit | `jsonb` для ответов, AI usage и audit details; GIN-индексы добавлять только после появления реальных запросов по ключам, чтобы не раздувать MVP. |
